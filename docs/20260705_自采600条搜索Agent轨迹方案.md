# 自采 600 条搜索 Agent 轨迹方案

> 日期：2026-07-05  
> 输入参考：`docs/部分方案.pdf`、`docs/20260705_HuggingFace搜索轨迹数据集调研报告.md`、`docs/buildSearch.md`、`docs/20260623_Agent轨迹构造与Judge微调数据调研报告.md`  
> 目标：从推荐的 3 个自采 task 数据集中采样约 600 条任务，使用 AutoGen + 魔搭 MCP 批量生成搜索 Agent 轨迹，为后续 SFT、DPO/GRPO 和 Agent Judge 数据构造做第一批数据底座。

---

## 1. 方案定位

从 `部分方案.pdf` 看，当前整体路线是：

- 先搭建搜索/代码智能体轨迹收集流程。
- 将轨迹转成 SFT 数据。
- 进一步构造 DPO、GRPO 或 Agent Judge 训练数据。
- 用 trajectory-level / step-level 评估体系筛选和反哺数据。

本方案只覆盖第一阶段：**搜索 Agent 自采轨迹**。第一批不追求一次性做全所有场景，而是先产出 600 条可审计、可复现、可过滤的轨迹。

---

## 2. 推荐采样结论

第一批建议只使用前一份调研中推荐的 3 个自采 task 源：

| 数据集 | 数据集 ID | 原始规模 | 第一批采样 | 角色 |
|--------|-----------|----------|------------|------|
| AssistantBench | `AssistantBench/AssistantBench` | 214 | 200 | 真实复杂 Web 任务 |
| WideSearch | `ByteDance-Seed/WideSearch` | 200 | 200 | 宽搜索、枚举、表格填充 |
| BrowseComp-ZH | `PALIN2018/BrowseComp-ZH` | 289 | 200 | 中文深搜索、多跳问答 |
| 合计 | - | 703 | 600 | - |

推荐采用 **200 / 200 / 200 均衡采样**，理由是：

1. 三个数据集规模都不大，第一批更适合做能力覆盖对比，而不是按原始规模比例抽样。
2. 三个数据集代表三种不同任务形态：真实委托、宽搜索、中文深搜索。
3. 均衡采样便于后续统计每类任务的成功率、平均工具调用次数、成本和轨迹质量。
4. AssistantBench 和 WideSearch 原始规模接近 200，采样几乎覆盖全量，更适合快速形成高价值任务池。

## 3. 采样方法

### 3.1 总体策略

目标不是“随机抽 600 条就跑”，而是构造一个可控的第一批任务池：

```text
主样本：600 条
├── AssistantBench: 200
├── WideSearch: 200
└── BrowseComp-ZH: 200

备份样本：约 80-100 条
├── AssistantBench 剩余 14 条
└── BrowseComp-ZH 剩余 60-80 条
```

建议实际执行时采用：

1. 先跑 **30 条 pilot**：每个数据集 10 条，验证 MCP 可用性、AutoGen 工具调用稳定性、日志格式和成本。
2. 再跑 **600 条主样本**。
3. 对失败轨迹做同源替换：AssistantBench 失败优先用 AssistantBench 剩余样本替换；BrowseComp-ZH 失败用 BrowseComp-ZH 剩余样本替换；WideSearch 因原始只有 200 条，失败时建议保留失败标签，或从 BrowseComp 英文版补充替代。

### 3.2 AssistantBench 采样

| 项 | 建议 |
|----|------|
| 采样数量 | 200 |
| 输入字段 | `task` |
| 参考字段 | `answer`, `gold_url`, `explanation`, `difficulty` |
| 采样方式 | 按 `difficulty` 分层；如果 difficulty 分布不可用，则按任务文本长度和是否包含明确 URL/实体分层 |
| 保留样本 | 剩余 14 条作为备份或小型验证集 |

推荐分层：

| 难度/形态 | 比例 | 数量 | 目的 |
|-----------|------|------|------|
| 简单直接搜索 | 20% | 40 | 保证基础成功率 |
| 中等多页面任务 | 50% | 100 | 第一批主力数据 |
| 高难长链任务 | 30% | 60 | 产生高价值长轨迹 |

AssistantBench 的任务更像真实用户委托，不能只要求 Agent 找一个短答案。轨迹中应要求 Agent：

- 拆解任务。
- 搜索多个候选来源。
- 读取页面正文。
- 必要时交叉验证。
- 给出最终答案和证据 URL。

### 3.3 WideSearch 采样

| 项 | 建议 |
|----|------|
| 采样数量 | 200 |
| 输入字段 | `query` |
| 参考字段 | `evaluation`, `language`, `instance_id` |
| 采样方式 | 原始规模正好 200，建议第一批全量采样 |
| 保留样本 | 不保留；用失败标签记录失败原因 |

WideSearch 的重点是“找全”，不是“找一个”。采样和执行时要保留语言分布：

- 英文任务：优先用于国际网页搜索。
- 中文任务：优先用于中文搜索。
- 表格/列表型任务：强制输出结构化结果。

WideSearch 轨迹应重点记录：

- query 分解。
- 多次搜索 query。
- 每次搜索覆盖的子目标。
- 已找到项、未找到项、重复项。
- 最终表格或列表。

### 3.4 BrowseComp-ZH 采样

| 项 | 建议 |
|----|------|
| 采样数量 | 200 |
| 输入字段 | `Question` |
| 参考字段 | `Topic`, `Answer` |
| 采样方式 | 按 `Topic` 分层等比例采样 |
| 保留样本 | 剩余 89 条作为中文验证集或失败替换池 |

BrowseComp-ZH 应优先保证 topic 覆盖，而不是完全随机。推荐采样步骤：

1. 统计所有 `Topic` 的样本数。
2. 每个 Topic 至少抽 1 条。
3. 剩余名额按 Topic 原始占比分配。
4. 对文本过短、答案可能已失效或问题歧义大的样本标记为低优先级。

BrowseComp-ZH 的轨迹要强调中文搜索行为：

- 中文 query rewrite。
- 中文网页读取。
- 中文证据摘录。
- 多源交叉验证。
- 最终中文回答。

## 4. 魔搭 MCP 选择

### 4.1 总体工具池

第一批不建议把所有 MCP 都暴露给同一个 Agent。建议拆成主工具和兜底工具：

| 能力 | 首选 MCP | 备用/增强 MCP | 说明 |
|------|----------|---------------|------|
| 中文/综合搜索 | `ZhipuAI/Zhipu-Web-Search` | 必应搜索中文 MCP | 中文任务优先 |
| 英文/国际搜索 | `@tavily-ai/tavily-mcp` 或 Brave Search MCP | Jina Search | WideSearch 英文任务优先 |
| 通用搜索+读取 | `@PsychArch/Jina-AI-MCP-Tools` | - | 当前项目已有测试脚本验证 `jina_search` / `jina_reader` |
| 网页正文读取 | `@modelcontextprotocol/fetch` | `jina_reader` | 默认 Fetch，失败再 Jina Reader |
| 动态网页 | `@Automata-Labs-team/MCP-Server-Playwright` | Chrome DevTools MCP | 只作为失败兜底，不进入默认路径 |
| 学术检索 | `@afrise/academic-search-mcp-server` | `@blazickjp/arxiv-mcp-server` | 只在任务明显是论文/学术时启用 |
| 地图/地点 | `@amap/amap-maps` | 百度地图 MCP | 只在任务明显涉及地点、路线、天气、POI 时启用 |

第一批最小可运行组合：

```text
必选:
1. @PsychArch/Jina-AI-MCP-Tools
2. @modelcontextprotocol/fetch

强烈建议:
3. ZhipuAI/Zhipu-Web-Search
4. @tavily-ai/tavily-mcp 或 Brave Search MCP

按需:
5. @Automata-Labs-team/MCP-Server-Playwright
6. @afrise/academic-search-mcp-server
7. @amap/amap-maps
```

### 4.2 三个数据集分别使用哪些 MCP

| 数据集 | 默认 MCP 路由 | 兜底 MCP | 不建议默认启用 |
|--------|---------------|----------|----------------|
| AssistantBench | Zhipu/Tavily/Jina Search + Fetch | Jina Reader、Playwright、Academic Search、Amap | 不要所有垂直 MCP 全开 |
| WideSearch | Tavily/Brave/Jina Search + Fetch | Zhipu、Jina Reader、Firecrawl/Playwright | 不要只用单次搜索 |
| BrowseComp-ZH | Zhipu Web Search + 必应搜索中文 + Fetch | Jina Reader、Playwright | 不要优先用英文搜索源 |

#### AssistantBench

推荐 Agent：

```text
AssistantBenchAgent
├── Zhipu Web Search
├── Tavily 或 Jina Search
├── Fetch
├── Jina Reader
└── 按任务路由启用 Academic / Amap / Playwright
```

适合原因：

- AssistantBench 任务开放度高，可能涉及普通网页、机构页面、论文、地点或实时网页。
- 需要先用通用搜索定位候选 URL，再读取正文。
- 任务失败常见原因是页面动态渲染或正文抽取失败，因此需要 Playwright 兜底，但不能默认调用。

建议规则：

```text
普通事实/机构/产品/人物：Zhipu/Tavily -> Fetch -> Jina Reader
论文/学术：Academic Search -> Fetch/Jina Reader
地点/天气/路线/POI：Amap -> 搜索补证据
Fetch 空内容/JS 页面：Playwright
```

#### WideSearch

推荐 Agent：

```text
WideSearchAgent
├── Tavily 或 Brave Search
├── Jina Search
├── Fetch
└── Jina Reader
```

适合原因：

- WideSearch 需要多 query、多页面、覆盖率检查。
- 英文和国际信息较多时，Tavily/Brave 比单纯中文搜索更合适。
- Jina Search + Reader 适合作为稳定的搜索读取组合。

建议规则：

```text
先让模型把 query 拆成 3-8 个子问题
每个子问题至少搜索 1 次
对候选 URL 去重
每个最终条目至少保留 1 个证据 URL
输出表格时必须包含 source_url 字段
```

WideSearch 不建议使用单一 `jina_search` 一次完成。轨迹价值来自多轮覆盖和修正。

#### BrowseComp-ZH

推荐 Agent：

```text
BrowseCompZHAgent
├── Zhipu Web Search
├── 必应搜索中文 MCP
├── Fetch
└── Jina Reader
```

适合原因：

- BrowseComp-ZH 是中文深搜索 benchmark，中文网页覆盖和中文 query rewrite 很关键。
- 智谱联网搜索适合作为中文综合搜索主入口。
- 必应搜索中文可作为免费补充和交叉验证。
- Fetch/Jina Reader 用于读取正文，不应只依赖搜索摘要。

建议规则：

```text
先用中文原问题搜索
如果结果弱，改写 2-3 个中文 query
必要时加入实体别名、年份、地点、机构名
至少读取 2 个来源
最终答案必须附证据 URL
```

## 5. AutoGen 轨迹产出流程

### 5.1 推荐 Agent 拆分

不要把十几个 MCP 全部挂到一个 `AssistantAgent` 上。建议按数据集或任务类型拆 Agent：

```text
TaskRouter
├── AssistantBenchAgent
├── WideSearchAgent
└── BrowseCompZHAgent
```

每个 Agent 的 system message 应明确：

- 必须先搜索再读取。
- 不能只根据搜索摘要回答。
- 每条结论必须有 source URL。
- 工具失败要重试或切换备用工具。
- 最终输出 JSON，便于后续自动解析。

### 5.2 单条轨迹标准流程

```text
输入 task
  ↓
任务分类与难度预估
  ↓
规划：拆解子问题和检索策略
  ↓
搜索：调用搜索 MCP
  ↓
读取：调用 Fetch 或 Jina Reader
  ↓
补搜：结果不足时改写 query
  ↓
综合：生成答案、证据、置信度
  ↓
质检：格式、证据、工具调用、答案覆盖
  ↓
保存轨迹
```

### 5.3 输出格式

建议每条轨迹保存为 JSONL：

```json
{
  "id": "assistantbench_000001",
  "source_dataset": "AssistantBench/AssistantBench",
  "source_id": "original row id",
  "task": "user task text",
  "gold_answer": "optional",
  "agent_name": "AssistantBenchAgent",
  "mcp_tools_enabled": ["zhipu_search", "jina_search", "fetch", "jina_reader"],
  "messages": [],
  "tool_calls": [
    {
      "step": 1,
      "tool": "jina_search",
      "args": {"query": "..."},
      "success": true,
      "latency_ms": 1200
    }
  ],
  "evidence": [
    {
      "url": "https://example.com",
      "title": "page title",
      "supporting_claim": "what this page supports"
    }
  ],
  "final_answer": "...",
  "quality": {
    "status": "accepted",
    "num_tool_calls": 6,
    "num_evidence_urls": 3,
    "failure_reason": null
  }
}
```

## 6. 质量过滤标准

第一批 600 条建议不要只看“是否有最终回答”，而要按轨迹质量过滤。

### 6.1 接受标准

| 数据集 | 最低工具调用 | 最低证据 URL | 特殊要求 |
|--------|--------------|--------------|----------|
| AssistantBench | 3 | 2 | 需要体现任务拆解或多来源确认 |
| WideSearch | 5 | 3 | 必须有子问题/子 query，输出列表或表格 |
| BrowseComp-ZH | 3 | 2 | 必须中文 query 或中文网页证据 |

通用接受标准：

- `messages` 完整记录 user、assistant、tool call、tool result、final answer。
- 至少一次搜索工具调用。
- 至少一次正文读取工具调用。
- final answer 不为空，且不能只复述搜索摘要。
- 证据 URL 可访问或至少在工具结果中出现。

### 6.2 拒绝标准

以下轨迹应标记为 rejected 或用于负样本，不进入第一批 SFT 正样本：

- 无工具调用直接回答。
- 只有搜索，没有读取正文。
- 工具失败后没有重试或降级。
- final answer 与证据明显不一致。
- WideSearch 没有覆盖多个条目。
- BrowseComp-ZH 全程只用英文 query，且没有中文证据。
- 输出格式无法解析。

### 6.3 失败替换规则

如果目标是最终得到 600 条 accepted 轨迹，建议这样替换：

```text
AssistantBench accepted < 200:
  用 AssistantBench 剩余 14 条补齐；
  仍不足时，从 BrowseComp-ZH 或 BrowseComp 英文版补。

WideSearch accepted < 200:
  优先保留失败轨迹用于负样本；
  正样本不足部分从 DeepWideSearch 或 BrowseComp 英文版补。

BrowseComp-ZH accepted < 200:
  从 BrowseComp-ZH 剩余 89 条补齐。
```

如果目标只是“采样约 600 条任务并产出轨迹”，则失败轨迹也应保存，后续可用于 Judge 负样本或过程奖励模型训练。

## 7. 成本与批处理建议

### 7.1 批处理节奏

推荐分三批跑：

| 批次 | 数量 | 目的 |
|------|------|------|
| Pilot | 30 | 每数据集 10 条，验证工具链、日志、格式和成本 |
| Batch-1 | 180 | 每数据集 60 条，修正 prompt 和路由 |
| Batch-2 | 390 | 跑完剩余主样本 |

不要一开始直接跑 600 条。第一批 pilot 很容易暴露：

- 工具 schema 不兼容。
- 模型不调用工具。
- 搜索结果质量差。
- Fetch 返回空内容。
- 输出 JSON 不稳定。
- 单条成本或耗时超预期。

### 7.2 工具调用上限

| 数据集 | 建议最大工具调用 | 超限处理 |
|--------|------------------|----------|
| AssistantBench | 10-12 | 要求总结已有证据并停止 |
| WideSearch | 12-18 | 每个子问题限制 top-k，避免无限扩展 |
| BrowseComp-ZH | 8-12 | 改写 query 最多 3 轮 |

### 7.3 运行参数建议

```text
temperature: 0.2-0.5
max_tool_iterations:
  AssistantBench: 12
  WideSearch: 18
  BrowseComp-ZH: 12
parallel_tool_calls: false
reflect_on_tool_use: true
每条任务 timeout: 3-8 分钟
```

`parallel_tool_calls` 建议先关闭，方便轨迹审计和后续构造 step-level 数据。

### 8.3 第一阶段最终推荐

第一阶段的最小可行路线：

1. 采样 `AssistantBench` 200 条、`WideSearch` 200 条、`BrowseComp-ZH` 200 条。
2. MCP 默认接入 `Jina-AI-MCP-Tools` + `Fetch`。
3. 中文任务增加 `Zhipu-Web-Search` 或必应搜索中文。
4. WideSearch 英文任务增加 `Tavily` 或 Brave Search。
5. 只在读取失败、动态网页或表单页面时调用 `Playwright`。
6. 每条轨迹必须保存完整 messages、tool calls、tool results、evidence URL 和 final answer。
7. 先跑 30 条 pilot，再跑 600 条主样本。

## 9. 关键判断

如果只能做一个最稳的起步版本，建议：

```text
数据:
AssistantBench 200 + WideSearch 200 + BrowseComp-ZH 200

MCP:
Jina-AI-MCP-Tools + Fetch + Zhipu-Web-Search + Tavily/Brave

执行:
AutoGen 三个专用 Agent，不做全工具大杂烩

验收:
600 条任务全部保留，accepted 轨迹单独筛出；
失败轨迹不要丢，后续可作为 Judge 负样本。
```

这条路线与当前 PDF 中“先做轨迹收集，再构造 SFT/DPO/GRPO/Judge 数据”的方向一致，同时避免第一批就陷入过多 MCP、过多数据源和过复杂浏览器环境。
