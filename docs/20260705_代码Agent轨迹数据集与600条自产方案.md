# 代码 Agent 轨迹数据集与 600 条自产方案

> 日期：2026-07-05  
> 目标：调研代码任务 task 来源、现成代码 Agent 轨迹来源，并结合 `mini-swe-agent + Microsoft universal devcontainer 镜像` 设计第一批约 600 条自产代码轨迹方案。  
> 核心约束：时间有限，尽量少选数据集；自产约 600 条；尽量覆盖多语言；后续可转 SFT / DPO / GRPO / Agent Judge 数据。

---

## 1. 结论摘要

如果第一阶段只做约 600 条代码自产轨迹，建议 **task 只选 2 个数据集**：

| 优先级 | 数据集 | HF ID | 采样数量 | 覆盖语言 | 角色 |
|--------|--------|-------|----------|----------|------|
| 1 | Multi-SWE-bench mini | `ByteDance-Seed/Multi-SWE-bench_mini` | 400 | Python, Java, TypeScript, JavaScript, Go, Rust, C, C++ | 多语言主数据源 |
| 2 | SWE-bench Lite | `princeton-nlp/SWE-bench_Lite` | 200 | Python | Python 成熟生态补充 |
| 合计 | - | - | 600 | 8 类主流语言 | 第一批自产任务池 |

现成代码轨迹建议优先只选 2 个，最多 3 个：

| 优先级 | 数据集 | HF ID | 推荐原因 |
|--------|--------|-------|----------|
| 1 | Multi-SWE-bench Trajectories | `ByteDance-Seed/Multi-SWE-bench_trajs` | 与自产 task 语言覆盖一致，可作为多语言轨迹参考 |
| 2 | SWE-agent trajectories | `nebius/SWE-agent-trajectories` | 80k 级 SWE-agent 风格轨迹，和 mini-swe-agent 路线接近 |
| 3，可选 | SWE-smith mini_swe_agent_plus trajectories | `Kwai-Klear/SWE-smith-mini_swe_agent_plus-trajectories-66k` | mini-swe-agent-plus 产出的 66k 轨迹，适合参考同类框架格式 |

不建议第一阶段引入太多代码数据集。代码任务的真实成本主要不在下载数据，而在仓库拉取、依赖安装、测试执行、超时处理、patch 验证和轨迹清洗。先用 2 个 task 源跑通闭环，比铺开 5-8 个数据源更稳。

## 2. mini-swe-agent 与 universal 镜像适配性分析

### 2.1 mini-swe-agent 定位

`mini-swe-agent` 是 SWE-agent 生态中的轻量代码 Agent 方案，适合执行 SWE-bench 类任务：给定 GitHub issue / problem statement，在仓库中定位代码、编辑文件、运行测试、生成 patch。

它适合本项目的原因：

- 与 SWE-bench / Multi-SWE-bench 这类 issue resolving task 天然匹配。
- 轨迹通常包含 shell 命令、文件查看、代码编辑、测试运行、错误修正和最终 patch。
- 相比重型 IDE Agent，更容易批量跑任务和记录统一轨迹。
- 与现成的 SWE-agent 轨迹数据在行为模式上接近，便于混合或对齐格式。

第一阶段建议把 mini-swe-agent 当作代码轨迹采集器，而不是直接追求 benchmark 高分。轨迹数据的价值在于完整过程：

```text
读 issue -> 探索仓库 -> 定位文件 -> 修改代码 -> 运行测试 -> 失败修正 -> 生成 patch
```

### 2.2 Microsoft universal devcontainer 镜像定位

Microsoft devcontainers 的 `universal` 镜像是通用开发容器基底，适合作为多语言任务的起点。它的优势是：

- 预装常见开发工具和多语言运行时，适合快速启动不同语言仓库。
- 与 devcontainer / VS Code / GitHub Codespaces 生态兼容。
- 对 Python、Node.js、Java、Go、C/C++、Rust 等主流语言任务更友好。
- 作为统一 sandbox 镜像，便于批量调度和隔离任务。

但它不能保证每个真实开源仓库“开箱即测”。Multi-SWE-bench 和 SWE-bench 的任务来自真实仓库，不同仓库常见问题包括：

- 依赖版本冲突。
- 需要系统库，例如 `libssl-dev`、`libpq-dev`、`cmake`、`pkg-config`。
- Node / Java / Rust / Go 版本要求不一致。
- 测试耗时长或需要网络。
- C/C++ 项目需要额外编译工具链和构建缓存。

因此建议将 universal 镜像作为 **base image**，而不是认为它能完全覆盖所有仓库。实际执行时需要三层策略：

```text
universal base image
  ↓
按语言安装缺失工具链和包管理器缓存
  ↓
按 repo 执行 setup/test 命令，并记录失败原因
```

### 2.3 对不同语言的适配判断

| 语言 | universal 镜像适配性 | 第一批建议 |
|------|----------------------|------------|
| Python | 高 | 作为稳定主力，SWE-bench Lite 补 200 条 |
| JavaScript / TypeScript | 高 | 依赖 npm/pnpm/yarn，需限制安装时间 |
| Java | 中高 | Maven/Gradle 项目可跑，但下载依赖耗时明显 |
| Go | 中高 | 工具链相对稳定，注意模块下载 |
| Rust | 中 | cargo 构建耗时较长，需较长 timeout |
| C / C++ | 中低 | 编译环境和系统库差异大，第一批可以采样但要限制数量 |

结论：`mini-swe-agent + universal` 可以支撑第一批多语言自产轨迹，但应把成功率目标定得现实一些。建议保留失败轨迹，用作 Judge 负样本或过程质量评估数据。

## 3. 代码 task 来源调研

### 3.1 推荐 task 数据集

#### 3.1.1 Multi-SWE-bench mini

| 属性 | 内容 |
|------|------|
| Hugging Face | https://huggingface.co/datasets/ByteDance-Seed/Multi-SWE-bench_mini |
| 数据集 ID | `ByteDance-Seed/Multi-SWE-bench_mini` |
| 规模 | 400 instances |
| 语言 | Python, Java, TypeScript, JavaScript, Go, Rust, C, C++ |
| 特点 | 每种语言 50 条，覆盖 easy / medium / hard |
| 推荐用途 | 第一批多语言自产 task 主来源 |

这是最适合你当前约束的数据集：一个数据集就覆盖 8 类语言，每种语言固定 50 条，总量正好 400。它能显著降低采样逻辑复杂度。

建议第一阶段 **全量采样 400 条**：

```text
Python       50
Java         50
TypeScript   50
JavaScript   50
Go           50
Rust         50
C            50
C++          50
```

优点：

- 多语言覆盖最好。
- 样本量适中。
- 不需要再从大数据集中复杂分层。
- 与现成 `Multi-SWE-bench_trajs` 可对齐分析。

风险：

- 部分语言环境搭建成本较高，尤其 C/C++/Rust。
- License 标记为 `other`，正式训练/发布前需要核查数据卡。

#### 3.1.2 SWE-bench Lite

| 属性 | 内容 |
|------|------|
| Hugging Face | https://huggingface.co/datasets/princeton-nlp/SWE-bench_Lite |
| 数据集 ID | `princeton-nlp/SWE-bench_Lite` |
| 规模 | 300 instances |
| 语言 | Python |
| 特点 | SWE-bench 子集，真实 GitHub issue resolving，生态成熟 |
| 推荐用途 | Python 任务补充，验证 mini-swe-agent 流程稳定性 |

SWE-bench Lite 虽然只覆盖 Python，但工具链、生态、评测方式和社区经验都最成熟。第一阶段建议从 300 条中采样 200 条，用于提高整体成功率和调试 pipeline。

建议采样：

```text
SWE-bench Lite: 200 / 300
保留 100 条作为失败替换池或小型验证集
```

选择 SWE-bench Lite 而不是完整 SWE-bench 的原因：

- 完整 SWE-bench 有 2,294 条，但第一阶段不需要这么大。
- Lite 的任务规模更适合快速调试 mini-swe-agent。
- Python 仓库依赖和测试相对更容易标准化。

### 3.2 可选但不建议第一批加入的数据集

| 数据集 | HF ID | 不优先加入原因 | 后续用途 |
|--------|-------|----------------|----------|
| SWE-bench Verified | `SWE-bench/SWE-bench_Verified` / `princeton-nlp/SWE-bench_Verified` | 500 条高质量评测集，容易造成评测污染 | 作为后续评估集，不建议自产训练用 |
| SWE-bench full | `princeton-nlp/SWE-bench` | Python 样本多但第一阶段工作量变大 | 第二阶段扩充 Python |
| Multi-SWE-bench full | `ByteDance-Seed/Multi-SWE-bench` | 1,632 条，多语言好但第一阶段过大 | 第二阶段按语言补样 |
| SWE-bench Pro | `ScaleAI/SWE-bench_Pro` | 企业级长程任务，复杂度高 | 后续高难轨迹 |
| SWE-Explore-Bench | `SWE-Explore-Bench/SWE-Explore-Bench` | 更偏仓库探索评估，不是直接修 issue 主任务 | 用于训练 repo exploration |

## 4. 600 条自产采样方案

### 4.1 最小数据集组合

第一阶段推荐：

```text
自产 task:
1. ByteDance-Seed/Multi-SWE-bench_mini: 400 条，全量
2. princeton-nlp/SWE-bench_Lite: 200 条，分层采样

总计: 600 条
```

这个组合的好处：

- 只接入 2 个 task 数据集，工作量低。
- 覆盖 8 类语言。
- Python 有额外 200 条，便于稳定跑通 pipeline。
- 与现成多语言轨迹和 SWE-agent 轨迹都有映射关系。

### 4.2 语言配比

| 来源 | 语言 | 数量 |
|------|------|------|
| Multi-SWE-bench mini | Python | 50 |
| Multi-SWE-bench mini | Java | 50 |
| Multi-SWE-bench mini | TypeScript | 50 |
| Multi-SWE-bench mini | JavaScript | 50 |
| Multi-SWE-bench mini | Go | 50 |
| Multi-SWE-bench mini | Rust | 50 |
| Multi-SWE-bench mini | C | 50 |
| Multi-SWE-bench mini | C++ | 50 |
| SWE-bench Lite | Python | 200 |
| 合计 | - | 600 |

最终语言占比：

```text
Python: 250
Java: 50
TypeScript: 50
JavaScript: 50
Go: 50
Rust: 50
C: 50
C++: 50
```

这个比例不是语言均衡，而是工程可行性优先。Python 多一些有两个价值：

- 更容易跑通 mini-swe-agent 采集流程。
- 方便与 SWE-agent 现成轨迹对齐，作为格式和质量基线。

### 4.3 采样细则

#### Multi-SWE-bench mini

建议全量使用 400 条，不再采样。

执行时按语言分批跑：

```text
Batch A: Python + JavaScript + TypeScript
Batch B: Go + Java
Batch C: Rust + C + C++
```

原因：

- Batch A 成功率预计最高，适合验证 pipeline。
- Batch B 依赖安装可控，但耗时可能增加。
- Batch C 编译和系统依赖风险最高，放最后。

#### SWE-bench Lite

建议从 300 条中采样 200 条：

| 层次 | 数量 | 规则 |
|------|------|------|
| 易/中等任务 | 120 | 优先 issue 描述清晰、测试命令明确、仓库依赖简单 |
| 难任务 | 50 | 保留一定长链修复轨迹 |
| 多仓库覆盖补齐 | 30 | 按 repo 去重补齐，避免集中在少数 repo |

如果没有难度字段，按代理指标分层：

- issue 文本长度。
- patch 涉及文件数量。
- repo 名称分布。
- test patch 是否复杂。
- problem statement 是否包含明确报错、函数名、模块名。

### 4.4 Pilot 方案

不要直接跑 600 条。建议先跑 40 条 pilot：

```text
Multi-SWE-bench mini:
8 语言 x 3 条 = 24 条

SWE-bench Lite:
16 条 Python

Pilot 合计: 40 条
```

Pilot 重点看：

- universal 镜像能否 clone / checkout / install。
- mini-swe-agent 是否能正确记录命令、文件编辑和测试。
- 每种语言平均耗时。
- 哪些语言需要额外工具链。
- 轨迹 JSON 是否能统一解析。
- 失败轨迹能否保留完整 error。

Pilot 通过后再跑主样本。

## 5. 自产轨迹执行方案

### 5.1 运行环境

建议以 universal 镜像为基础，额外做一个项目自定义镜像：

```text
mcr.microsoft.com/devcontainers/universal:<tag>
  + git / gh / curl / jq
  + python/uv/pip cache
  + node/pnpm/yarn cache
  + maven/gradle cache
  + go module cache
  + rust toolchain/cache
  + cmake/ninja/build-essential/pkg-config
  + mini-swe-agent runtime
```

不要让每条任务都从零安装所有语言依赖。建议按语言准备缓存卷：

```text
cache/
├── pip/
├── npm/
├── pnpm/
├── maven/
├── gradle/
├── go/
├── cargo/
└── ccache/
```

### 5.2 mini-swe-agent 单条任务流程

```text
读取 task
  ↓
准备仓库：clone / checkout base commit
  ↓
启动 universal sandbox
  ↓
mini-swe-agent 读取 issue / problem_statement
  ↓
探索仓库：ls / grep / rg / cat / sed
  ↓
编辑代码：patch / file edit
  ↓
运行相关测试
  ↓
失败则继续定位和修正
  ↓
生成 final patch
  ↓
保存轨迹、patch、测试日志、状态
```

### 5.3 轨迹保存格式

建议每条自产轨迹保存为 JSONL：

```json
{
  "id": "multi_swe_mini_python_0001",
  "source_dataset": "ByteDance-Seed/Multi-SWE-bench_mini",
  "language": "Python",
  "repo": "owner/repo",
  "base_commit": "commit_sha",
  "problem_statement": "...",
  "agent": "mini-swe-agent",
  "sandbox_image": "mcr.microsoft.com/devcontainers/universal:<tag>",
  "messages": [],
  "actions": [
    {
      "step": 1,
      "type": "shell",
      "command": "rg \"error message\" .",
      "observation": "...",
      "exit_code": 0
    }
  ],
  "patch": "diff --git ...",
  "tests": {
    "commands": ["pytest ..."],
    "passed": true,
    "logs": "..."
  },
  "quality": {
    "status": "accepted",
    "resolved": true,
    "num_steps": 18,
    "failure_reason": null
  }
}
```

### 5.4 接受与拒绝标准

Accepted 正样本最低标准：

- 有完整 action-observation 轨迹。
- 至少查看过仓库文件。
- 至少产生一次代码修改。
- 最终 patch 非空。
- 至少运行一次测试或静态检查。
- 测试通过，或明确说明无法运行测试但 patch 逻辑可解释。

Rejected / 负样本标准：

- 没有探索仓库就直接写 patch。
- patch 为空。
- 修改无关文件。
- 测试失败且没有二次修正。
- 安装依赖失败后无降级尝试。
- 超时、OOM、仓库无法 checkout。

失败轨迹不要丢。代码 Agent Judge 很需要失败样本，例如：

- 依赖安装失败。
- 搜索定位错误。
- patch 编译失败。
- 测试命令选择错误。
- 过早提交答案。

## 8. 风险与控制

### 8.1 环境风险

多语言代码任务最大风险是环境，不是模型。建议每条任务记录：

- 镜像 tag。
- repo checkout commit。
- 依赖安装命令。
- 测试命令。
- 系统包缺失。
- 超时时间。
- exit code。

### 8.2 评测污染风险

SWE-bench Verified 和 Multi-SWE-bench 可能被用作公开评测。自产训练数据和评测集必须分离。建议：

- 第一阶段不使用 SWE-bench Verified 训练。
- 如果后续评估 Multi-SWE-bench full，要从训练来源 blacklist 已跑过的 mini 样本。
- 每条轨迹保存 `source_dataset` 和 `instance_id`。

### 8.3 成本风险

代码轨迹比搜索轨迹更贵：

- 仓库 clone 耗时。
- 依赖安装耗时。
- 测试运行耗时。
- C/C++/Rust 编译耗时。

建议设置：

| 语言 | 单任务 timeout |
|------|----------------|
| Python | 20-30 min |
